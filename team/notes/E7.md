## What was built

1. **`engine/cosmicmass/checkpoint.py`** (new). One `.npz` file holds everything the time loop carries: the columns of the state (taken by name, so the columns of D37 will be saved without a change), the acceleration, fields and inertia the step context remembers, the momentum given to the walls, the temperatures, and one JSON text with the step, the last time step, the rows of the time series, the first measurement, the counters of the walls, of the inflow and of the heat bath, and the state of the random generator. It is read with `allow_pickle=False`: a checkpoint is data and cannot run code. It is written beside its name and moved into place, so a run killed while writing leaves the previous checkpoint whole.
2. **The run key.** A checkpoint carries a SHA-256 of the stamp (without the run id, the T0 status and `checkpoint_every`) and of the initial state. A run with other settings, other bodies or another engine commit refuses it.
3. **`runner.run(..., resume, checkpoint, progress, should_stop)`**, all optional and keyword-only: every earlier call is unchanged. `numerics.checkpoint_every = k` writes `results/<scenario>/checkpoint.npz` every k steps; the file is removed when the run ends, and git ignores it. `should_stop()` is asked after every step; when it says yes the run writes a checkpoint and raises `Interrupted`.
4. **The command line:** `--resume [FILE]`, `--progress`, and Ctrl-C now stops the run after the step it is in, with a checkpoint and exit code 130.
5. **Step control** (`numerics.drift_tolerance`, off by default): the "halve dt and repeat the step" of `ARCHITECTURE.md`, section 6, which was drawn but never built. See the choices below.
6. **`stamp.t0_status()`**: the stamp's `t0_status` is no longer always "not run". See the choices below.
7. **`stamp.validate_outputs()`**: `write_results` checks the stamp and the summary against the P4 schemas and refuses to write files that break them (`ResultsError`).
8. Schema additions (`engine/schemas/stamp.schema.json`): the optional `resumed_at_steps` of a run stamp, and the two new keys of `numerics`.

## Choices I made (labelled assumptions, for the maintainer; questions 26 to 28)

The sponsor asked me to answer my own questions with the best option and keep working. These are the options I took. None changes an existing run: with the new settings left out, the runner computes exactly what it computed before.

1. **What "the same result" means.** I took the strict reading: the resumed run writes the same `summary.json` and the same `timeseries.csv`, byte for byte, and ends in the same state, bit for bit. This is why the checkpoint also saves the step context's remembered acceleration: after a velocity Verlet step it was computed with the half-step velocity, so for a law that reads the velocity (L6), computing it again from the saved state would not give the same number.
2. **A resumed run says so.** Its stamp gains `resumed_at_steps` (for example `[2533]`). The summary does not change, so "the same stamp re-run gives the same summary" still holds.
3. **What `t0_status` means (question 26).** A stamp says "pass" when, for each of T0.1 to T0.5, the newest stored run whose engine code is the same as the current one passed. "The same engine code" is `git diff --quiet <that run's commit> <this commit> -- engine/cosmicmass`. So the commit that stores the T0 results, and any later commit that does not touch the engine, read "pass"; a commit that changes the engine reads "not run" until T0 is run on it again. With changed files ("-dirty") and outside git it is "not run". The alternative, "T0 passed on exactly this commit", can never be true, because the results are committed after the run.
4. **Step control (question 27).** The watched quantity is the energy the law conserves (E9: Real plus Composer where D23 defines it, otherwise the Real energy), measured before and after the step, before the environment acts. A step that changes it by more than `drift_tolerance` (relative) is repeated from the same state with half the time step, at most 10 times; after that it is kept and counted (`gave_up`). The summary reports `step_control: {drift_tolerance, repeated, gave_up}`. It costs two energy sums per step, which is why it is off by default.
5. **The schema check is soft (question 28).** `jsonschema` is a development dependency (D24) and the schema files live in `engine/schemas/`, outside the installed package. Where either is missing (an installed copy, the browser), the check is skipped and `tools/validate_results.py` in CI remains the check. Making it hard would need `jsonschema` as a runtime pin and the schemas inside the package: a decision for the maintainer.
6. **The checkpoint is not a result.** It lives beside the run folders, is ignored by git, and is never read by anything but `--resume`.

## Progress (newest first)

- 2026-11-14: built, tested, documented. A first version of the run key used the stamp only; a test showed that a run with a body moved resumed another run's checkpoint, because the stamp names the bodies but not where they are. The key now includes the initial state. A second slip found by the tests: the loop over wall events reused the name of the key variable, so a run with walls wrote checkpoints it could not read back.

## Results (software checks; nothing here is a finding)

- **Interrupted and resumed, the same result:** five scenes (an eccentric pair with the adaptive step; a gas in a box with reflecting walls, an inflow, a heat bath and a seeded population; the same with absorbing walls; two bodies in a second field with the Boris push; a pair under L1a with the screened range) are stopped at step 57, between two checkpoints, and resumed. `summary.json` and `timeseries.csv` are identical byte for byte, and the final state bit for bit.
- A run killed between two checkpoints resumes from the last periodic one and gives the same result; a run interrupted twice gives the same result and its stamp says `[31, 71]`.
- From the command line, by hand: a 3,000-step gas run interrupted by a real Ctrl-C at step 2,533 and resumed gave the same two files as the uninterrupted run (`cmp`).
- A checkpoint of other numerics, of other bodies, of another format, an unreadable file and a missing file are each refused with a message that says why.
- Step control on an eccentric pair at a fixed step of 0.05: the energy drift over the run falls by more than a factor of 10 at a tolerance of 1e-6, and every recorded step is within the tolerance. With a tolerance never reached, the run is the same as without step control, row for row.
- `t0_status`: "not run" with nothing stored, with one test missing, with changed files, outside git; "pass" with five passes on the same engine code; "fail" when the newest matching run of one test failed.
- A stamp with a wrong `law.sign` is refused and no folder is created.
- Tests: 27 new in `engine/tests/test_checkpoint.py`. Whole suite on Linux, Python 3.12.3: **340 passed**, 1 deselected (slow), coverage 99% (`checkpoint.py`, `runner.py` and `stamp.py` at 100%). `ruff check`, `ruff format --check`, `tools/check_architecture.py --base origin/main` and `tools/validate_results.py` (23 run folders) pass.
- One test of another component changed: `engine/tests/test_web_universe.py` now puts the runner's `engine_commit` back after it imports the browser bridge. The bridge replaces it with `web-v<version>` for the whole process, which did not matter until the outputs were checked against the schema (question 28).
